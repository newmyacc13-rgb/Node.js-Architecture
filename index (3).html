Every team meets the same wall eventually. The dashboards look civilized — p50 in the low twenties, CPU flat, no alerts — and then a routine Monday puts a vertical line through the p99. Someone adds a cache. The line bends for a week and then bends back. The next fix arrives with a vendor attached.

We spent two quarters on the unglamorous version of that problem: keep the topology fixed and rebuild the path a request takes through a Node.js service. The estate is 41 services on Node 24 LTS, undici 7 at the egress layer, a shared Redis 8 tier, three regions, and a peak of roughly 92k requests per second at the edge. No new region, no new cluster, no rewrite. The result was a p99 of 61 ms against a 214 ms baseline, 38% less CPU per request, and one fewer cache cluster for someone to get paged about at 3 a.m.

What follows is the notebook, not the whitepaper: the budget we argued about, the loop discipline that survived load, the socket settings that mattered, the cache topology we settled on, and the serialization boundary that made the rest hold. Everything here is measured on production traffic or a replay of it.

01 — BudgetA latency budget you can actually defend

The first useful artifact was not a cache. It was a spreadsheet that assigned every millisecond in the request path to a team. Before that, "the API is slow" was a group project with no owner. After it, a regression had a name and a pager rotation attached.

The budget below is for the synchronous path of a read-heavy endpoint at p99: TLS and the first byte from the edge, admission and queueing, identity and policy, the handler plus origin call, serialization, and the response write. The numbers are the negotiated ceilings; the observed column is what the fleet actually spent after the work in this article.

Two conventions made the table usable. First, every stage is measured at its boundary with a histogram, never with an average; a mean hides the only number anyone feels. Second, a budget that is exceeded twice in a rolling hour opens an incident automatically, even if the user-facing SLO still looks green. Latency debt compounds quietly, and the only defense is to treat the first 5 ms of drift as the incident.

Working rule

If a millisecond does not have an owner, it does not have a budget. If it does not have a budget, it will be spent by someone else's dependency.

One more discipline: budget p99, not p50. At our volume, p50 is a solved problem and will stay solved unless someone ships a synchronous filesystem call. Every hour of the two quarters went into the tail, because the tail is where the queueing, the garbage collector, the cold sockets, and the unlucky cache keys live.

02 — RuntimeThe event loop is a single-lane road

Node's concurrency model is honest about its constraint: one thread executes JavaScript, and everything else waits in line behind it. At 2k requests per second per instance, a 40 ms synchronous block is not a hiccup — it is a 40 ms tax on every request that arrives during it, and the tax is paid in arrival order, which is exactly how a tail gets made.

We found four recurring offenders. A synchronous crypto call in a token verifier (3–11 ms per request under load). A JSON body parser configured without a size ceiling, occasionally asked to chew through a 6 MB payload. A price calculator that ran a deep clone over a catalog object graph. And a logger that formatted strings with a regular expression on the hot path. None of them were visible in CPU flame graphs at low traffic; all of them were obvious in the event-loop delay histogram.

The instrument we trust most is boring: monitorEventLoopDelay with a 10 ms resolution, exported as a p99 gauge per instance. A healthy service holds p99 event-loop delay under about 15 ms. Above that, no amount of cache tuning will save the tail, because the process is not accepting work while the loop is blocked.

perf/loop.jsJavaScript
import { monitorEventLoopDelay, PerformanceObserver } from 'node:perf_hooks';

// A sidecar timer, not a per-request hook. Resolution is cheap; cardinality is not.
const delay = monitorEventLoopDelay({ resolution: 10 });
delay.enable();

setInterval(() => {
  const p99 = delay.percentile(99) / 1e6; // ns → ms
  metrics.gauge('runtime.event_loop.p99_ms', p99);
  if (p99 > 15) log.warn({ p99 }, 'loop saturated');
  delay.reset();
}, 10_000).unref();

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    metrics.observe('runtime.gc.pause_ms', entry.duration);
  }
}).observe({ type: 'gc', buffered: true });

The fixes were less glamorous than the diagnosis. Token verification moved to a worker pool with a queue-depth cap; the parser got an 800 KB ceiling and a 413 response that the client team actually preferred; the catalog clone became a structural share plus a shallow copy; the logger moved to precompiled prefixes. The loop delay p99 fell from 47 ms to 11 ms on the busiest service, and its p99 latency fell 30% before we touched a single socket or cache.

Node 24 helps here in a quiet way: AsyncLocalStorage now runs on AsyncContextFrame by default, which cut the overhead of our tracing context propagation by roughly a third and removed a class of context-loss bugs in callback-heavy code. It is not a feature you demo. It is a feature that lets you leave the tracer on.

03 — TransportSockets are state, not plumbing

Once the loop was honest, the next largest line item was connection setup. Default undici behavior is reasonable for a script and expensive for a fleet: short keep-alive windows, a conservative per-origin connection cap, and no opinion about address-family selection. Under a 92k req/s peak, "reasonable" produced repeated TLS handshakes and a long tail of requests waiting for a socket that was about to be recycled.

Three settings did most of the work. Keep-alive moved to 30 s with a 120 s ceiling, which matches the idle timeout our load balancer actually enforces instead of the library's guess. The per-origin cap went to 128, sized with Little's law from observed concurrency rather than a round number. Pipelining stayed at 1: raising it above 1 buys throughput on paper and pays for it in head-of-line blocking, and we had already met that bill once.

runtime/dispatcher.tsTypeScript
import { Agent, setGlobalDispatcher } from 'undici';

setGlobalDispatcher(new Agent({
  keepAliveTimeout: 30_000,
  keepAliveMaxTimeout: 120_000,
  connections: 128,          // per origin, from Little's law
  pipelining: 1,             // >1 trades tail latency for throughput
  allowH2: true,             // opt-in on 7.x; default in 8.x
  connectTimeout: 1_500,
  headersTimeout: 4_000,
  bodyTimeout: 8_000,
  autoSelectFamily: true,     // happy-eyeballs over v4/v6
}));

const res = await fetch(url, {
  signal: AbortSignal.timeout(800),
  headers: { accept: 'application/cbor, application/json;q=0.9' },
});

The abort budget matters as much as the socket budget. Every outbound call carries an AbortSignal with a deadline shorter than the caller's own deadline; a request that cannot finish inside its slice is cancelled and retried elsewhere rather than allowed to occupy a socket until the client gives up. We cap retries at one, require idempotency keys for writes, and count cancellations as a first-class outcome — not as errors to be swept under a dashboard.

HTTP/2 was a mixed story, and the version matters. Node 24 ships undici 7, where h2 is opt-in (allowH2 defaults to false) and a session effectively runs one stream at a time. The multiplexing work landed in undici 8.4 and 8.5 in mid-2026: one session now carries requests up to the origin's SETTINGS_MAX_CONCURRENT_STREAMS, and 8.5 extended that to POST bodies, which had been serializing behind a non-idempotent guard. We pinned 7.29 for the quarter and re-rolled h2 on 8.x after a load run that specifically held a streaming response open — the exact shape that used to queue everything behind it.

The DNS detail nobody budgets for

We run a small in-process resolver cache with a 30 s TTL and a hard cap on entries, and we pre-warm it on boot for the handful of origins on the critical path. The savings are modest in the median and significant exactly when it matters: during a rolling deploy, when a cold process would otherwise pay a recursive lookup inside the first request's budget.

04 — CacheTwo tiers, one truth

Our first cache was a shared Redis cluster used for everything, which is a good way to turn a latency problem into a network problem with a single point of blame. The second design splits responsibilities: an in-process L1 for the tiny, hot, immutable-ish objects that most requests need, and a shared L2 for everything cross-instance and durable.

L1 is an LRU with a byte ceiling, not an entry ceiling. Sixty-four megabytes per instance, TTLs between 2 and 30 seconds, and a strict rule that nothing user-specific ever enters it. On our read mix that yields an 84% hit rate, which removes the majority of round trips before they happen. L2 is Redis 8 with client-side tracking enabled, keys versioned by schema (v7:product:8841), and per-key jitter on expirations so a fleet of instances does not all expire the same popular key in the same millisecond.

The piece that made the topology stable was single-flight: when a key misses, exactly one caller per process goes to L2 and origin, and every concurrent caller awaits the same promise. Without it, a hot key expiring under load produces a thundering herd that looks like a database incident and is really a coordination bug.

cache/get-or-set.tsTypeScript
const pending = new Map<string, Promise<unknown>>();

async function getOrSet<T>(key: string, ttlMs: number, load: () => Promise<T>): Promise<T> {
  const hit = local.get<T>(key);
  if (hit !== undefined) return hit.value;

  const inflight = pending.get(key) as Promise<T> | undefined;
  if (inflight) return inflight;

  const p = (async () => {
    const wire = await redis.getBuffer(key);
    if (wire) {
      const value = decode<T>(wire);
      local.set(key, value, { ttl: jitter(ttlMs) });
      return value;
    }

    const fresh = await load();
    await redis.set(key, encode(fresh), 'PX', ttlMs + 5_000);
    local.set(key, fresh, { ttl: jitter(ttlMs) });
    return fresh;
  })().finally(() => pending.delete(key));

  pending.set(key, p);
  return p;
}

Stale-while-revalidate completes the picture for the catalog endpoints that tolerate a few seconds of staleness: serve the stale value immediately, refresh in the background, and let the TTL be a freshness target rather than a cliff. We keep a separate, short negative cache for misses (5 s) so a deleted product does not hammer the origin, with the obvious guard that a null is stored explicitly and never confused with "not cached."

Failure we earned

Our first L1 rollout used unversioned keys and no invalidation path. A price update took 40 minutes to reach every instance, and the incident review was shorter than the customer email thread. Version keys by schema, publish invalidations on a channel, and assume every cache is a replica with a lag you must bound.

05 — SerializationStop paying the JSON tax twice

Here is the uncomfortable arithmetic of a read path: the origin already has the data as objects, we serialize it to JSON for the cache, parse it back on a miss, serialize it again for the response, and parse it a third time in the client. On a 1.4 KB record at 90k req/s, that is a measurable share of CPU spent converting between representations we designed ourselves.

The fix was not "replace JSON." JSON remains the right answer for public HTTP surfaces: debuggable, cacheable by intermediaries, understood by every client, and stable in ways binary formats are not. The fix was to stop using one codec for every boundary. We split the estate into three lanes:

  • Edge-facing responses stay JSON, negotiated normally, compressed with Brotli at quality 4–5 for dynamic bodies. Debuggability is a feature and the CPU cost is acceptable at the edge.
  • Service-to-service and cache payloads use CBOR, which keeps a JSON-like data model (no schema compilation step), cuts wire size by roughly 20%, and decodes faster than JSON for our shapes.
  • Fixed, high-volume records — telemetry envelopes, internal event batches — use Protobuf, where the schema is stable and the codegen is already in the build.

Every cached buffer carries a two-byte envelope: a version and a codec identifier. That is enough to roll a codec change without a flag day, and enough to reject a buffer that a newer instance wrote in a format an older one cannot read. The envelope is the difference between a migration and an outage.

codec/envelope.tsTypeScript
const CODEC = { json: 1, cbor: 2, protobuf: 3 } as const;

export function encode<T>(value: T, codec: keyof typeof CODEC): Buffer {
  const body = codec === 'json'
    ? Buffer.from(JSON.stringify(value))
    : cborEncode(value);

  return Buffer.concat([Buffer.from([0x01, CODEC[codec]]), body]);
}

export function decode<T>(buf: Buffer): T {
  const [, codec] = buf;                    // byte 0 is the envelope version
  const body = buf.subarray(2);

  return codec === CODEC.json
    ? JSON.parse(body.toString('utf8'))
    : cborDecode(body);
}
ops/verify-envelope.tsTypeScript

Compression interacts with all of this and is easy to get wrong. Below about 1 KB, compressing a response costs more CPU than it saves in bytes; we leave small payloads alone. Above that, we precompress static assets once at build time, compress dynamic JSON with Brotli quality 4–5, and use Zstandard for large internal batches. Zstd ships inside Node's zlib but is still flagged experimental in 24.x, and dictionary support only arrived in 24.6 — so pin the patch level before you bet a cache tier on it. Trained dictionaries are the part worth the trouble: on repetitive JSON shapes they cut small-payload size by another fifth, which is exactly the regime where per-message compression usually loses. Cache entries store the compressed bytes alongside the codec tag, so a hit never re-compresses.

The result on the read path was an 8 ms p99 reduction in serialization and a 6% drop in fleet CPU, but the more valuable outcome was legibility: the profiler stopped showing JSON.parse as the top frame, which meant the next optimization had somewhere else to land.

06 — TelemetryInstrument the boundary, not the app

Every optimization in this article was found by a histogram, not by intuition. The instrumentation that earned its keep is narrow: per-route latency histograms at the server boundary, event-loop delay and GC pause per instance, cache hit ratio split by tier, serialization time as its own span, and outbound call duration bucketed by origin. Fifty-eight metrics, not five thousand.

Two conventions matter. First, use histograms and export percentiles at query time; pre-aggregated averages are how you end up with a dashboard that is green while the p99 is on fire. Second, attach exemplars — a trace ID on the slowest bucket — so the person on call can jump from "the tail moved" to a specific request in one click. An alert without an exemplar is a rumor with a threshold.

We also track a metric that is not about the service at all: the p99 of the gap between "request accepted" and "first byte written." It catches the failure mode where the loop is fine, the origin is fine, and the response is late because something outside the request path — a cron, a GC heap walk, a large log flush — is borrowing the process. That number moved from 8 ms to 2 ms once the loop work landed, and it has been the first chart in every review since.

07 — RolloutThe order that survived contact

Sequence mattered more than any individual change. Caching before loop discipline hides the loop problem behind a shorter path. Serialization work before caching optimizes buffers that the cache would have eliminated. And socket tuning before either is tuning a pipe that the process cannot keep full.

  1. Instrument first. Per-route histograms, loop delay, GC pauses, cache-tier hit ratios, serialization spans. Two weeks of baseline with no changes except the instrumentation itself.
  2. Fix the loop. Move synchronous crypto and compression to workers, cap request bodies, remove hot-path regular expressions, and set a p99 delay alert at 15 ms.
  3. Tune the transport. Keep-alive aligned to the load balancer, per-origin connection caps from Little's law, abort budgets on every outbound call, pre-warmed DNS for critical origins.
  4. Add L1, carefully. Versioned keys, byte-bounded LRU, jittered TTLs, explicit invalidation channel, and a kill switch that bypasses the tier entirely.
  5. Negotiate the codec. Envelope every cached buffer, roll CBOR internally first, keep JSON at the edge, and never migrate two layers in the same deploy.
  6. Re-baseline, then stop. Hold the new shape for a month of load runs before chasing the next 10 ms. Most of our remaining tail is origin time, and origin time is somebody else's budget.

The results, measured the same way as the baseline: p50 from 24 ms to 11 ms, p95 from 71 ms to 28 ms, p99 from 214 ms to 61 ms. CPU per request fell 38%, Redis operations fell 64% because L1 absorbed the redundancy, and the monthly cache bill dropped enough that the finance team asked what we had turned off.

What did not work

Pipelining at 10 bought 4% throughput and cost 30 ms of p99 under mixed payload sizes. CBOR on the public API broke every internal debugging session for a week; negotiation solved it. A global TTL of 60 seconds created synchronized expiry every minute and a stampede we could set a watch to. A second Redis cluster improved one chart and added a failure domain we did not need.

08 — ClosingWhat we would do differently

We would start with the budget and the loop, and we would resist the temptation to open with the cache. We would write the envelope and the key-versioning rules before the first set, not after the first stale price. We would treat the event-loop delay chart as a first-class SLO rather than a debugging artifact. And we would spend less time arguing about codecs and more time measuring the shapes we actually serve.

The honest summary is that none of this is exotic. There is no secret flag, no magic library, no architectural rewrite. There is a single-threaded runtime doing exactly what it says, a network path with state you can size, a cache with failure modes you can bound, and a serialization boundary you can move out of the hot path. Do those four things in that order, measure each one at its boundary, and the tail comes down.

P99 is a feature. Staff it like one.

Appendix — MethodReproducing the numbers

The production figures are p99s from an eight-week rolling window on the read endpoint, measured at the edge proxy and split by region. The load figures come from a fixed harness: three runs per configuration, c7g.2xlarge hosts, 480 concurrent connections, a 60-second warm-up and a 15-minute steady state on a replay of a weekday traffic mix. Percentiles are computed from the raw latency arrays, never from pre-aggregated averages, and the confidence intervals are 95% Wilson intervals on the proportion of requests that exceed a stage budget.

bench/run.shShell
#!/usr/bin/env bash
set -euo pipefail

nvm use 24.21.0 >/dev/null   # pin the patch, not the major

# 480 connections, 60 s warm-up, 15 min steady state, replay mix.
autocannon -c 480 -d 900 --warmup 60 \
  -m GET -H 'accept-encoding: br, gzip' \
  http://localhost:8080/api/v7/catalog?sku=8841 \
  | tee "runs/$(date +%F)-read.json"

node perf/percentiles.mjs runs/*-read.json --p 50,95,99 --ci wilson

Codec timings were taken separately, outside the server, over 10,000 iterations per format with the record shape frozen in a fixture. That removes network and framework noise but flatters every codec equally — which is the point of comparing them, and the reason none of those numbers belong in a capacity plan.
